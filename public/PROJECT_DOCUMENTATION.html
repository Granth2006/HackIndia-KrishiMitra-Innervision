1. Project Overview

KrishiMitra AI v2 is a modernized web application designed for Indian farmers. It provides AI-powered agricultural tools including automated irrigation scheduling, plant disease detection, crop recommendations, an AI chatbot, weather forecasts, and a farmer marketplace.

Primary Feature: The Automatic Sprinkler System — upload a plant image → AI detects diseases → recommends watering schedule, pesticide, and farming tips → downloadable report.

Target Users

  • Indian farmers (rural/semi-urban), possibly low-tech savvy
  • Design: Very simple UI, large buttons, high contrast, earthy colors, minimal text, icons-first
  • Supports 18 Indian languages via Google Translate

5. Detailed Feature Breakdown

5.1 Authentication System

File: AuthContext.jsx, LoginModal.jsx

User clicks "Get Started"
→
LoginModal opens
→
Google renderButton / Guest btn


Google JWT decoded (atob)
→
{name, email, picture} → localStorage
→
Navigate to /dashboard

How Google Sign-In Works:

  1. index.html loads the GIS SDK: accounts.google.com/gsi/client
  2. When LoginModal mounts, useEffect calls google.accounts.id.initialize() with the client ID
  3. google.accounts.id.renderButton() renders Google's official sign-in button in a ref container
  4. User clicks → Google popup opens → user selects account → JWT credential returned
  5. JWT is decoded client-side: JSON.parse(atob(credential.split('.')[1]))
  6. User data stored in localStorage('krishimitra_user')

Guest Mode:

Stores {name: 'Guest', email: 'guest@krishimitra.ai'} in localStorage. Same flow, just no Google interaction.

⚠️ Important: For Google Sign-In to work on your Vercel domain, you must add it to Authorized JavaScript Origins in Google Cloud Console → APIs & Services → Credentials → OAuth 2.0 Client.

Soil Data System:

The API has a hardcoded mapping of Indian cities → states → soil properties (pH, nitrogen, phosphorus, potassium, texture). This avoids needing a soil database API. 40+ cities are mapped.

5.6 Weather Forecast

File: Weather.jsx (client-side only, no serverless function)

  • Uses browser navigator.geolocation on mount to auto-detect location
  • Reverse geocode via Nominatim API to get city name
  • Fetches current weather + 5-day forecast from OpenWeatherMap
  • Displays: temperature, humidity, wind, rain, pressure, feels-like, visibility
  • City search: user can type any city and fetch its weather
Note: The Weather API key (WEATHER_API_KEY) is used client-side in Weather.jsx and server-side in crop-recommend.js. For production, consider proxying weather calls through a serverless function too.

6. Serverless API Routes (Vercel Functions)

All 3 files in /api/ are auto-deployed as Vercel serverless functions. Each exports a handler(req, res).

Endpoint Method Model Input Output
/api/analyze-plant POST llama-4-scout (vision) {mode, imageBase64, mimeType} JSON: disease + irrigation + pesticide
/api/chat POST kimi-k2 (text) / llama-4-scout (image) {messages, userMessage, imageBase64?} {reply: "..."}
/api/crop-recommend POST kimi-k2 (text only) {location, farm_size, farm_size_unit, last_crop, crop_type} {crops: [...]}

Why Two AI Models?

moonshotai/kimi-k2-instruct — Text-only model with very high RPM (requests per minute) and RPD (requests per day). Used for chatbot text and crop recommendations where no image is involved.

meta-llama/llama-4-scout-17b-16e-instruct — Vision-capable model that accepts image_url content type. Used whenever an image needs to be analyzed (Sprinkler, Disease, Chatbot with image). kimi-k2 does NOT support image inputs — sending arrays to it causes "content must be a string" error.

9. Deployment & Environment

Production Deployment (Vercel)

npx vercel --prod --yes

This command: builds the Vite app → uploads to Vercel CDN → deploys /api/*.js as serverless functions → aliases to production URL.

Environment Variables (set via Vercel Dashboard or CLI):

Variable Where Used Purpose
GROQ_API_KEY_1 All 3 serverless functions Authenticates with Groq API
WEATHER_API_KEY crop-recommend.js OpenWeatherMap API for crop weather data

Local Development

# Terminal 1 — API server (mirrors Vercel functions)
npm run dev:api        # → Express on localhost:3001

# Terminal 2 — Frontend
npm run dev            # → Vite on localhost:5173 (proxies /api → :3001)

Why not vercel dev?

Vercel CLI's dev mode has a known compatibility issue with Vite 7.x — it fails to parse HTML files through Vite's import analysis plugin. The proxy approach (Vite → Express) works identically and is the standard Vite development workflow.

vercel.json Configuration:

{
  "buildCommand": "npm run build",
  "outputDirectory": "dist",
  "framework": "vite",
  "rewrites": [
    { "source": "/api/(.*)", "destination": "/api/$1" },
    { "source": "/((?!api/).*)", "destination": "/index.html" }
  ]
}

The rewrite rules: API calls pass through to serverless functions; everything else serves index.html (SPA fallback for React Router).

10. Security Considerations

Concern How We Handle It
API key exposure Groq keys are in Vercel env vars, never in frontend code
Google OAuth JWT token decoded client-side; credential verification via Google's SDK
CORS Serverless functions set Access-Control-Allow-Origin: *
Image uploads Base64 encoded in browser, sent via POST body — no file storage
Data persistence All user data in localStorage (client-only, no database)

12. Key Design Decisions

Decision Rationale
localStorage over database No backend infra needed; works offline; target users may have intermittent connectivity
Serverless over Flask Zero maintenance, auto-scaling, free tier; Flask was only needed for local dev
Two AI models kimi-k2 has better RPM limits for text; llama-4-scout is needed for vision — kimi-k2 cannot accept images
Google Translate over i18n 18 languages without any translation files; simpler for rapid development
CSS variables over Tailwind Full control over design system; no build-time dependency; easier dark mode
Framer Motion over CSS animations Mount/unmount animations; spring physics; gesture support
